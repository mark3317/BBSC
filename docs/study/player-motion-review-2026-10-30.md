## Путь данных

Штатная игра → импорты PS4 socket → guest_net.cpp P2PSocketSendTo → DatagramSocket::SendTo →
FramingCodec::EncodeDatagram (включая защиту) → Transport::SendPacket → direct/UDP relay.
Обратно: Transport::ThreadMain → Relay::Receive (если relay) → FramingCodec::Decode →
HandleDatagram → очередь vport → DatagramSocket::RecvFrom → штатный обработчик игры.
Принадлежность каждого внутреннего вида пакета позиции/анимации/боевым событиям здесь не расшифрована.
Внешний транспорт понимает framing и vport, но не смысл обновлений движения.
TCP streams также поддерживаются поверх физического UDP; нельзя объявлять любой игровой пакет снимком позиции.

BBSC Follow/WorldFlags/Life через собственный TCP relay — отдельные потоки. Периодический Follow
служит для переходов между картами, а не для покадровой репликации удалённого персонажа.
TickBbscJoinTeleport — однократная установка гостя при входе, а не непрерывное сглаживание движения.

## Находки и оценка

1. p2p_relay.cpp Route / NoteDirectReceive / Receive: по умолчанию force=true, сначала возможны
   direct-копии, затем relay. direct_rx и relay_seen — исторические bool без срока свежести.
   Появление пакета через путь не доказывает его устойчивость сейчас; копии разных путей способны
   прибывать в другом порядке. Это кандидат на измерение и возможную стабилизацию выбора пути,
   НЕ доказанная причина freeze. Менять транспорт без NAT/rejoin/3-player контроля рискованно.
2. p2p_transport.h: очередь datagram 40 KiB на vport. HandleDatagram при переполнении отбрасывает
   новое, сохраняя старый FIFO. Если игра отстаёт, возможна обработка устаревшего состояния.
   Факт переполнения в проблемном прогоне неизвестен. Увеличение очереди способно увеличить задержку;
   удаление старых пакетов вслепую способно потерять события. До распознавания полных snapshot-пакетов
   и их sequence/delta-зависимостей политику очереди оставлять без изменения.
3. ThreadMain ожидает readability socket, а не опрашивает движение раз в секунду: секундный deadline
   нужен для обслуживания relay. Его уменьшение само по себе не увеличит частоту сетевых позиций.
4. Собственная интерполяция/экстраполяция требует изучить native receiver, существующее сглаживание,
   timestamp/sequence, teleport/death/load discontinuities и разделение render/physics transform.
   Запись поверх физической позиции может конфликтовать с анимациями, hitbox и коллизиями;
   добавленный визуальный буфер добавит задержку. Пока высокорисковое изменение, не вносить.
5. Нет основания увеличивать частоту Follow/WorldFlags либо переводить движение на TCP:
   они не заменяют штатную репликацию; TCP retransmission может задержать следующие обновления.
