# T18 — чаши: идентичность мира и изоляция состояния

30.10.2026. Пользователь попросил начать реализацию кооператива в чашах по текущей
логике мода. Четыре старых случая (PT-5, PT-14, PT-10, инструмент рун у друзей)
закрыты по прямому подтверждению пользователя; новой проверки этих случаев не требуется.

## Архитектура и реализованный первый этап

Используется существующий транспорт BBSC и его авторитет хоста, game-thread follow,
pre-load world flags, own-world snapshot, личный лут и общая death/recovery логика.
Новой сетевой службы, переписывания алтарей или отдельного цикла смертей нет.

- `core/bbsc_chalice.h`: ключ подземелья = ChannelId + FNV64 decoded FormData +
  размер + версия формата. Номер алтаря не входит в ключ. Карта хранится отдельно;
  идентификацию реального слоя внутри генерации ещё нужно подтвердить.
- Native reader читает выбранный алтарь, не меняя его. Адреса восстановлены по
  локальному неизменённому CUSA03173 v1.09 eboot.elf (см. ниже). Варианты без
  однозначного выбора/доступного буфера остаются unknown, размеры ограничены.
- Follow для m29 несёт 24-байтный ключ; обычный follow остаётся прежним. Гость
  сверяет свой native key, свежий follow и ключ полного снимка хоста. Поздний
  снимок предыдущей чаши не может переопределить новую идентичность follow.
- WorldFlags v3 = прежний пакет + ключ в каждом чанке (1042 байта до envelope).
  Сборка снимка различает map/snapshot/key; смешанные чанки и старые unscoped m29
  отклоняются. Обычные v1 и Dream v2 сохранены. Отправляется активная карта чаши,
  а не несуществующий общий мир всех её шаблонов.
- Вызовы общего RequestBbscSessionWarp в m29 требуют matching identity/снимка;
  таймаут не разрешает загрузку на своих флагах. Поиск совпадающего алтаря сам по
  себе не доказывает, что генерация загружена: первый вход остаётся штатным.
- Личные подборы: отдельный `guest-items/taken-<user>-<slot>-chalice-<channel>-<hash>-<version>-<size>-<map>.bin`.
  Legacy m29-биты обычного журнала не переносятся в новые чаши. Смена namespace
  сначала сохраняет старый журнал, при неудачной записи не уничтожает его.
- Подборы чаш не отмечают предметы своей чаши в own-world; её kind 5 при возврате
  восстанавливается точно, а не OR с чужим dungeon. Исключение m29 из Shared
  Progress остаётся. Общая логика сохранения реального инвентаря/наград сохранена.

**Граница этапа:** это основа для штатного призыва в заранее созданное одинаковое
подземелье. Автоматическое получение/монтирование FormData хоста из Сна, смена
подземелий с одинаковой картой, точный layer ID, полное прохождение слоёв и
прогресс одной общей чаши ещё не объявлены реализованными или проверенными.
Фильтры NPC/device в m29 не сняты вслепую. Нативный первичный призыв остаётся
штатным; новые guard относятся к загрузкам/записи состояния со стороны BBSC.
Обоим игрокам нужна эта сборка; старый клиент не понимает v3 и не получает гарантий изоляции.

## Доказательства native layout (локальный eboot)

- `019280A4..019281A7`: `[0553E9E8]` SprjHolygrail, count 7, `+8` массив алтарей.
- `01AC3E70..01AC3EE7`: выбранный алтарь по 7-битному полю event flags 9020;
  штатный код выбирает старший установленный бит. Reader требует один бит, иначе unknown.
- `01AB4569..01AB457C`: объект алтаря `+108` = CSDungeonRitualHelper.
- `01AA53AB..01AA53FD`: helper `+D0` ссылается на cached channel item,
  полученный `01E65290`; это **не** transient JSON object.
- `01E67200..01E67242`: cached item имеет vtable/+8 refcount, ChannelId `+10`.
- `01E67C20..01E67CD9`: decoded FormData owned buffer `+58`, byte length `+60`.
- `01E89F53..01E89F71`: JSON parser допускает FormDataVersion 0.
  Его временная структура имеет другой layout: `+0` channel, `+C` Status,
  `+10/+18` FormData. Её offsets не используются для cached item.

Статическое доказательство layout не доказывает, что selected altar совпадает с
runtime world гостя после призыва. Первый прогон должен установить это; при
несовпадении новая логика не подменяет данные выбранного алтаря догадками.

## Проверки

`tools/test_chalice_scope.py` компилирует реальные функции reader, sender, receiver,
follow callback, load readiness и scope switch с C++ memory fixture. Проверяет
разные алтари одного dungeon, другой ChannelId/FormData, неизвестную версию,
границы размера, полный/неполный/перемешанный снимок, malformed/legacy пакеты,
свежесть, old snapshot vs new follow identity, запрет Dream-to-dungeon без native
entry, смену namespace и сохранение при отказе записи. Это не игровой тест.
Существующие follow-arrival, post-load recovery (15), perf-policy и pending-work
проверки прошли до последних дополнений протокола; финальный прогон/сборка ниже.

## Следующие шаги реализации

1. По первому native призыву установить runtime идентичность/карту/слой на обеих
   машинах, наличие native FormData у гостя и корректность scoped журнала.
2. Трассировать штатный вход алтаря (SprjDungeonGateIns / CSDungeonRitualHelper)
   и загрузку генерации. Реализовать временный borrowed dungeon context хоста,
   не перезаписывая постоянный алтарь/ритуал/материалы гостя; увязать с own-world
   и восстановлением после краша. Только после этого разрешать автоматический вход из Сна.
3. Добавить достоверный layer ID в world/follow/loot scope, если packed map его
   не различает; подключить переходы и вайпы через общий механизм загрузок.
4. Проверить другая чаша с тем же шаблоном, корневые/обряды, третий игрок,
   лут/материалы/боссы/эхо и возврат/повторный призыв. Политику сохранения
   прогресса общей чаши отделить от восстановления своей чаши гостя.

## Первый игровой тест (текущие сейвы, без отката)

ПК — хост testHost, ноут — гость test. Пользователь создаст фиксированную Птумеру.
Для первого этапа создать/иметь **одинаковую чашу у обоих**, желательно на разных
алтарях. Войти штатно на первый слой и призвать гостя. Проверить видимость друг
друга, врагов, рычаг/дверь и по одному личному предмету. После босса попробовать
следующий слой; если гость не следует — записать, где остался, без ручных правок
сейва. Затем печать → свой мир → проверить чашу/предметы → повторный призыв.
При зависании/вылете оставить процессы для сбора; иначе закрыть обе игры и
написать «готово» с наблюдениями. Собирать CHALICE/FOLLOW/WORLD/ITEMS/DEATH.

Сборка и деплой: ожидают финальной проверки; этот раздел будет дополнен результатом.
